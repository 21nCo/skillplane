## Summary

The MCP can read or mutate knowledge and notes only after a context already
exists and the caller already knows its ID or slug. Context discovery, creation,
metadata updates, archive/restore lifecycle, and knowledge-revision history are
available to first-party HTTP/UI clients but not to MCP agents.

This forces a human or separate API client to bootstrap and maintain contexts,
which prevents an authorized agent using a skill from managing the contextual
knowledge that makes that skill relevant to a repository, project, customer, or
environment.

## Requirements

1. Add `contexts_list`, an authenticated read-only MCP tool that cursor-paginates
   active, archived, or all contexts for one authorized skill without requiring
   a context identifier.
2. Add `context_create`, an authenticated mutation that atomically creates a
   context and its first immutable knowledge revision with idempotency and full
   caller attribution.
3. Add `context_update`, an authenticated metadata-only mutation for name, type,
   external reference, description, and metadata. Require the context's exact
   previously observed `updatedAt` value to prevent last-write-wins races.
4. Add separate `context_archive` and `context_restore` authenticated lifecycle
   mutations. Require idempotency and the exact previously observed `updatedAt`
   value for concurrency safety.
5. Add `context_knowledge_history`, an authenticated read-only tool that
   cursor-paginates immutable knowledge revisions and returns safe provenance,
   digests, learning metadata, and Markdown.
6. Preserve `context_get`, `context_knowledge_update`, `context_notes_list`, and
   `context_note_upsert` compatibility.
7. All new tools must enforce tenant/skill ownership, OAuth or service-principal
   `contexts:read` / `contexts:write` scopes, strict schemas, filter-bound opaque
   cursors, caller attribution, idempotency, and fail-closed durable audit.
8. Context lifecycle mutations must write their permanent domain audit event in
   the same database transaction as the mutation; an audit failure must roll
   back the mutation.
9. Update schema, conformance, integration, security, documentation, production
   verification, and live tool inventory coverage.
10. Commit and push the implementation, deploy the MCP Worker, and verify the
    production context lifecycle through a fresh authorized MCP connection.

## Acceptance Criteria

- An agent can traverse `workspaces_list` to `skills_list` to `contexts_list`
  without receiving an out-of-band context ID.
- An authorized writer can create a context, update its metadata, revise its
  knowledge, list knowledge history, archive it, and restore it using MCP only.
- Stale metadata or lifecycle writes return a stable conflict with the current
  `updatedAt` and do not overwrite newer state.
- Viewers and credentials missing `contexts:write` cannot mutate contexts.
- Cross-workspace and cross-skill selectors reveal no private context data.
- Replayed idempotency keys return the original result, while changed payloads
  with the same key fail safely.
- Production advertises and successfully executes all new context tools.
