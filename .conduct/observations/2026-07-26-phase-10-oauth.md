# PHASE_10 OAuth and consent observations

## Consent workflow

The consent page presents one unambiguous decision. The client name is the
heading, while the canonical MCP resource and return host are separate,
readable facts. The requested scopes are listed individually with
plain-language permission descriptions rather than collapsed into an opaque
scope string.

Approve and deny are explicit buttons. Approval posts the signed request and
AuthFn CSRF value to the OAuth consent route; it does not construct an
authorization code in the browser. The browser then receives the exact
registered callback with the original state and an opaque one-time code.

Loopback callbacks receive a distinct amber warning that names the
`localhost:9876` destination and tells the user to proceed only when they
started a local agent connection. This warning is present in both themes.

## Protocol observations

- Authorization-server metadata advertises only authorization code, refresh
  token, query response mode, public token endpoints, and PKCE S256.
- Both protected-resource metadata paths return the canonical
  `https://mcp.skillplane.dev/mcp` resource and
  `https://app.skillplane.dev` authorization server.
- OpenID Connect discovery returns `404`; no ID token or OIDC claim surface is
  implied.
- An unauthenticated authorization request resumes only through a signed,
  relative `/oauth/consent` return path after AuthFn sign-in.
- Consent denial returns the original state with `access_denied` and no code.
- Approval, exchange, refresh, verification, and revocation use the real Hono,
  AuthFn, and local Postgres paths.

## Security observations

The successful E2E operational event contained only component, event type,
request ID, outcome, user ID, and client ID. It contained no authorization
request, code, verifier, token, refresh family secret, cookie, or CSRF value.

Database inspection and integration tests independently confirmed that issued
codes and tokens do not appear in schema columns or persisted row values.
Refresh replay invalidated the newly rotated access token and created a
redacted `oauth.refresh.reuse_detected` audit event.
