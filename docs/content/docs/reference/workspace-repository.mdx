---
title: Workspace repository layout
description: The canonical Git repository tree for a workspace's published skills and the skillplane.workspace.json index.
---

A workspace's current published skills can be rendered as a plain repository tree. The same tree is the contract for workspace Git sync: Git sources read it back without creating any version.

Write it to a directory with the CLI:

```sh
skillplane export --git ./workspace-skills
```

The command reads the primary workspace of the current project, local or cloud. Any credential that can list a cloud workspace's skills exports every non-archived published skill in it, whatever its visibility, including private skills. All reads finish before anything is written. If a skill is published, republished, archived, renamed or reshared while the export reads the workspace, the export fails with `EXPORT_STATE_CHANGED`; run it again.

## Layout

```text
.gitattributes
skillplane.workspace.json
skills/
  deploy/
    SKILL.md
    scripts/ship.sh
    skill.json
  review/
    SKILL.md
    references/checklist.md
    skill.json
```

- `skills/<slug>/` is named by the skill's workspace slug and holds exactly the files of the skill's current published version: `SKILL.md`, `skill.json`, and any `skill.lock.json`, `README.md`, `LICENSE`, `assets/`, `references/`, `scripts/`, `templates/`, `agents/` or `verification/` entries the bundle contains. Paths follow the same allowlist as uploaded bundles.
- `skillplane.workspace.json` indexes the exported skills.
- `.gitattributes` contains `* -text`, so Git commits and checks out exported files without converting line endings, whatever `core.autocrlf` is set to. Skill directories never contain their own Git control files, so nothing in the tree overrides it. A `.git/info/attributes` file in your clone still takes precedence; do not set text or filter attributes there.

## What is exported

Every skill that is not archived and has a published version, at its current published version, whatever its visibility.

Never exported: drafts and pending or rejected candidates, archived skills, skills with no published version, instructions documents, contexts and their knowledge or notes, skill groups, Git source bindings, members, credentials or other secrets, analytics, and audit events.

Local workspaces have no sharing settings, so their skills are listed as `private`.

## `skillplane.workspace.json`

```json
{
  "formatVersion": 1,
  "skills": [
    {
      "digest": "sha256:6eeddf8bbda8d99685e6243821206e934cd30f084b09a5f02dd8e9a0727b6ca7",
      "id": "skill:c3fd5596-434d-4875-a9b3-cbacfdc6ce05",
      "path": "skills/deploy",
      "semanticVersion": "1.0.0",
      "slug": "deploy",
      "tags": ["ops"],
      "visibility": "workspace"
    }
  ]
}
```

| Field                      | Meaning                                                              |
| -------------------------- | -------------------------------------------------------------------- |
| `formatVersion`            | Layout version; currently `1`                                        |
| `skills[].id`              | Stable workspace skill ID                                            |
| `skills[].slug`            | Skill slug, also the directory name                                  |
| `skills[].path`            | Repository-relative skill directory, `skills/<slug>`                 |
| `skills[].visibility`      | `private`, `workspace`, or `public`                                  |
| `skills[].tags`            | Tags of the published version                                        |
| `skills[].semanticVersion` | Semantic version of the current published version                    |
| `skills[].digest`          | Canonical digest of that version, which the skill directory produces |

Skills are ordered by slug. No other fields are written.

## Determinism

The same workspace state always produces the same bytes, and therefore the same Git tree hash:

- Files and manifest entries are sorted by their UTF-8 bytes; JSON keys are sorted.
- The manifest is two-space indented JSON with LF line endings and a final newline.
- No timestamps, export times, or machine details are written, so the time zone and clock do not matter.
- Skill files are copied byte for byte from the canonical bundle, including any CRLF line endings they were published with. Rewriting them would change the digest.

Canonicalizing a skill directory reproduces `digest` exactly. The export fails rather than write a directory that would not.

## Skills that cannot be exported

The export fails with `EXPORT_INVALID`, naming the skill and the reason, and writes nothing, when any published skill would not read back unchanged through a Git source or cannot be written as a directory tree. A skill is refused when:

- its published bundle declares a slug other than the skill's workspace slug, because Git sources match a bound skill by the bundle's slug;
- a path segment is a Git control name, compared case-insensitively and including NTFS and HFS+ aliases such as `git~1`: `.git`, `.gitattributes`, `.gitignore` or `.gitmodules`, at any depth, because Git would not commit such a file byte for byte, or would drop or convert the files around it;
- a file or directory other than its root `SKILL.md` is named `SKILL.md`, such as `templates/SKILL.md` or `templates/SKILL.md/example.txt`, because Git sources treat every tree entry named `SKILL.md` as a separate skill root;
- a file looks like a credential, such as a private key or a GitHub or AWS access token;
- it has more than 197 files with distinct contents, a file larger than 5 MiB, or more than 20 MiB of files;
- one path is both a file and a directory, such as `assets/a` and `assets/a/b.txt`, or two paths differ only by letter case or Unicode normalization.

Publish a new version without the offending files, then export again.

## Reading the tree with Git sources

A Git source that imports the repository discovers each `skills/<slug>/` directory:

- In a workspace that already has these skills but no bindings, every entry is a **conflict** with its matching slug. Skills are never attached silently.
- After each path is bound to its skill with **Bind an existing workspace skill**, every entry is **unchanged**, and applying the preview creates no version.

A Git source that imports the whole repository is limited to 32 skills, 20 MiB of files in total, and 200 GitHub requests, one per distinct file plus three. The preview of a larger export fails as a whole. Create a source for each skill path, such as `skills/review`, instead.

## Writing into an existing directory

The target directory must not exist or must be empty; an existing `.git` entry is allowed. Use `--force` to export into a non-empty directory, such as a clone of the repository:

```sh
skillplane export --git ./workspace-skills --force
```

`--force` replaces only `skills/`, `skillplane.workspace.json`, and `.gitattributes`. Other entries, such as `.git` or `README.md`, are left alone. Skills that are no longer exported disappear from `skills/`.

The new tree is first written to a temporary `.skillplane-export-*` directory inside the target. Only once every file is written are the existing entries moved aside into that directory and the new ones moved in. If any step fails, the moved entries are put back and the export fails with `EXPORT_WRITE_FAILED`, so the directory is left as it was. In the unlikely case that they cannot be put back, the export fails with `EXPORT_RESTORE_FAILED` and names the directory that holds them. If the process is killed while entries are being replaced, the previous entries are in `.skillplane-export-*/previous`: restore them or run the export again with `--force`, then delete the leftover directory before committing.

A target that is itself a file or a symbolic link is refused with `EXPORT_TARGET_INVALID`. Its parent directories may be symbolic links, and a missing target is created.

On Windows, a skill whose slug is a reserved device name, such as `con` or `aux`, cannot be checked out.
